# Bounded live broadcast email transport

This transport is dedicated to the explicitly enabled broadcast pilot. The generic MSG91 notification provider still refuses live delivery. SMS and WhatsApp are not implemented here. A verified provider sender/domain, reviewed template, current consent, school allowlist, destination-hash allowlist and the durable submission ledger are prerequisites; this implementation does not enable them or send a test message.

The shared `notification.broadcast.live` configuration gates the pilot. Additional properties under `notification.broadcast.live.email` are `sender-email`, `sender-name`, `domain`, `template-id`, and `template-verified` (default false). The sender address must belong to that exact domain. `notification.msg91.auth-key` supplies credentials; no caller, sender-profile row or generic endpoint setting can override the fixed endpoint. The template must be reviewed for the fixed `title` and `message` variables, which contain HTML-escaped text. No raw HTML, recipient variables, attachments, CC/BCC, reply-to or arbitrary payload passthrough is supported.

The request is a single-recipient JSON POST to `https://control.msg91.com/api/v5/email/send`. It follows the [official email send contract](https://docs.msg91.com/email/send-email). A strict HTTP 200 success with `hasError:false`, empty `errors`, and a UUID in `data.unique_id` records **ACCEPTED**, meaning queued. It does not record delivery. The response example is present in that page's embedded `pageContentDataSSR.sampleResponse` data.

The 51-character stable event correlation is sent in `recipients[0].to[0].CRQID`, following the [case-sensitive email correlation contract](https://msg91.com/help/email/how-to-send-the-crqid-via-email-api). It is correlation only; MSG91 does not document duplicate suppression for this field. Authenticated, bound [email delivery reports](https://msg91.com/help/webhook-new/how-to-receive-email-delivery-reports-via-webhook-new) are a separate outcome.

The JDK client has a three-second connect timeout, ten-second overall deadline, no redirects, a 64 KiB request limit and a 16 KiB response limit. The body publisher permits one subscription, preventing automatic body replay even if other JVM code changes retry settings. The application makes one request and never retries it. Transport exceptions, malformed/contradictory responses, redirects, 408/409/425/429 and server failures become **UNKNOWN**. Explicit HTTP 400/401/403/404/405/413/415/422 refusals become **REJECTED**. An HTTP 200 error body without a documented positive acceptance remains UNKNOWN. None of these states permits blind resubmission.

Submission refuses an active database transaction. The worker must durably reserve the attempt before invoking it outside the transaction, then record the result. Prepared request bodies exist only in memory; their record string representation is redacted. The ledger receives the canonical request, destination and sender SHA-256 values, correlation and provider receipt, not raw contacts/body/auth headers. Exceptions and upstream response bodies are neither logged nor attached to returned errors.

Offline verification: `Msg91BroadcastLiveProviderTest` exercises the injectable transport without network calls; `Msg91NotificationDeliveryProviderTest` verifies the generic live block remains intact.
