# School notice review and delivery checks

Broadcasts now have a policy-backed recipient workflow. Its only executable mode is **DRY_RUN**. The default mode is **OFF**; live sending remains unavailable. No live provider configuration or external school data was changed by this implementation.

## Supported workflow

1. A superadmin creates a school-scoped `SCHOOL_NOTICE` for `ALL_PARENTS`, meaning primary guardians. SMS, email and WhatsApp are the admitted policy channels. Staff, whole-school, push and unclassified legacy drafts cannot dispatch.
2. Preview asks school-core for the school's current students and primary guardians. Eligibility requires an active guardian, enabled notification preference, verified contact, a guardian-specific current `SCHOOL_COMMUNICATIONS` consent grant, consent lawful basis, notice version and unexpired consent. Results expose counts and exclusion reasons without contact destinations. The review limit is 10,000 students; exceeding it fails the entire preview rather than silently selecting a partial audience.
3. Approval resolves the audience again and requires the exact preview fingerprint. A changed guardian, contact, consent decision, student selection or eligibility requires another review. A durable manifest records the school, student, channel, guardian, contact hash and approval evidence. Shared destinations are deduplicated per channel. A replay does not replace that manifest or add recipients.
4. Queueing changes the broadcast to `QUEUED`, never `SENT`. The manifest rows are the transactional outbox: approval and queue state are committed with their parent broadcast. A row-locking worker claims due recipients in a school-scoped transaction.
5. Before **every attempt**, the worker calls school-core again for the approved student/channel. Revocation, preference changes or unavailable student records suppress the attempt. A changed approved guardian/contact binding also suppresses it; the worker does not redirect an approved notice to a newly edited address.
6. An allowed check enters the existing persistent notification inbox, policy guard, provider and delivery-attempt audit pipeline. The stable key is `broadcast:{broadcastId}:{studentId}:{channel}`. Inbox terminal states replay without another provider attempt. Generic inbox retries exclude broadcast keys so they cannot retry stale evidence without this worker's fresh policy read.
7. The dashboard displays per-recipient dry-run, exclusion, duplicate, retry or dead-letter outcomes. Failed checks retry with bounded exponential backoff and an eight-attempt limit. Manual retry advances only failed nonterminal checks using their existing keys. Dry-run completion and provider processing never become recipient delivery receipts.

## Configuration and trust boundary

- Platform: `BROADCAST_DISPATCH_MODE=OFF` by default. `DRY_RUN` is the only recognized processing mode; any other value is treated as off.
- Platform and school-core: `BROADCAST_POLICY_TOKEN` is blank by default and must match for the authenticated internal policy call. A blank or incorrect credential fails closed. The credential is never exposed to the browser.
- Platform reuses `SCHOOL_CORE_URL` and Cloud Run audience-bound OIDC when calling a `.run.app` host. School-core's private `/api/v1/internal/notifications/broadcast-recipients` endpoint also requires the dedicated shared token and scopes database reads to the supplied school with RLS bypass explicitly disabled. Gateway internal-route rejection remains in place.
- `BROADCAST_DISPATCH_FIXED_DELAY_MS` defaults to 30,000. Queue processing also requires the existing notification delivery configuration to report dry-run mode. A configuration change cannot turn an already queued dry run into a live send.
- `BROADCAST_WORKER_READY=false` by default. An administrator must verify the authenticated request-driven schedule before enabling this readiness acknowledgement. Cloud Run with minimum instances zero and CPU throttling cannot reliably execute an in-process timer while idle. The existing private `POST /api/v1/internal/async/drain` now also drains broadcasts and returns `broadcastChecksAttempted`; its existing IAM boundary and Scheduler wiring are unchanged. Each broadcast drain attempts at most 25 recipients and starts no additional attempt after a 20-second budget. A currently running policy request retains its bounded network timeout.
- Public preview, approval, queue, retry and outcomes routes retain service-token, tenant-role and permission guards. Browser-supplied actor IDs, destinations and evidence are not trusted. No new gateway prefix is needed.

## Live provider blocker

Broadcast current-consent revalidation is now implemented at the authoritative school-core boundary. The existing MSG91 provider remains deliberately live-disabled. Its request correlation value (`CRQID`) has no documented duplicate-suppression guarantee in the repository's admitted provider contract. Treating it as an idempotency key would allow duplicate sends after ambiguous timeouts or a crash between provider acceptance and local persistence.

Before implementing live delivery, the provider contract must establish the idempotency key scope, retention period, replay behavior, timeout reconciliation and a way to distinguish acceptance from recipient delivery. The live implementation must carry the approved recipient binding and fresh policy decision through that path and verify configuration/template/channel eligibility. Existing live-startup and live-send guards must not be removed merely because the dry-run workflow passes. No live delivery receipt or successful external send is claimed here.
