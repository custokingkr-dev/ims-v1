# Source Project Deletion — Continuity and Credential Plan

**Prepared:** 2026-08-18 IST
**Premise:** `custoking` will be **deleted** after the migration. There is no rollback target and no
lingering tether. Everything must live in `custoking-dev` and `custoking-prod`.
**Companions:** `GCP-SPLIT-PROJECT-MIGRATION-PLAN-2026-08-18.md`,
`GCP-MIGRATION-DATA-LEDGER-PROD-2026-08-18.md`
**Method:** read-only live discovery. PostgreSQL was read through a temporary `postgres:16-alpine` Cloud
Run job with `SET default_transaction_read_only = on`; the job was deleted afterwards. No secret **values**
were exported, printed, or stored — only version metadata.

Emails, school UUIDs, Drive folder IDs, and object keys are omitted and held in restricted evidence.

## 2. Login credentials — what actually survives

**All user passwords survive the migration unchanged.** They are BCrypt hashes stored in the database, not
in any GCP-managed store, so they move with the dump.

Verified in production:

| Fact | Value |
| --- | --- |
| Password storage | `identity.app_users.password_hash` |
| Hash algorithm | **BCrypt `$2a$` — all 49 users, no legacy algorithms** |
| Users | 49 total: ADMIN 31 (12 active), SUPERADMIN 14 (1 active), OPERATIONS 4 (all active) — **17 active** |
| Roles defined | 8: SUPERADMIN (75 perms), ADMIN (63), SCHOOL_ADMIN (63), ZONE_ADMIN (26), OPERATIONS (23), VIEWER (22), ACCOUNTANT (17), TEACHER (7) |
| Scoped RBAC | `identity.user_role_assignments`, 109 rows, scoped by `school_id` / `zone_id` with validity and revocation columns |
| Sessions | 575 rows, **378 unexpired**, spanning 2026-08-07 → 2026-08-17 |
| Schools | 11 in `tenant_school.schools`; users carry 12 distinct `branch_id`, 0 `zone_id` |

Two consequences:

- **Students do not log in.** 1,257 students against 49 user accounts; authentication is staff and admin
  only. The "school login credentials" are `app_users` rows with scoped role assignments, and they migrate
  intact with the database.
- **The coarse `app_users.role` column is not the real authorization model.** SCHOOL_ADMIN, TEACHER,
  ACCOUNTANT, VIEWER and ZONE_ADMIN appear only in `user_role_assignments`. Any verification that checks
  only `app_users.role` will wrongly conclude those roles are unused.

## 3. Secrets — transfer values, do not regenerate

All 44 secrets carry **exactly one enabled version**. `jwt-secret-prod` also has one destroyed version
(rotated 2026-07-05), proving rotation works.

| Secret | Must the *value* carry over? | If regenerated instead |
| --- | --- | --- |
| `jwt-secret-{env}` | **Yes, to avoid disruption** | All **378 unexpired sessions** are invalidated; every active user is logged out and must sign in again. Not data loss — but decide deliberately, don't discover it. |
| `db-password-{env}` | **Yes** | Must equal the password of the `appuser` role you create on the destination instance, or Flyway cannot connect. |
| `app-rt-password-{env}` | **Yes** | Must equal the password passed to `create-app-rt-role.sql`, or every service fails to authenticate at runtime. |
| `superadmin-password-{env}` | Yes | Bootstrap credential paired with `seed-superadmin-sql`. |
| 11 inter-service read/ingest tokens | Yes, or rotate **all services atomically** | A partial rotation breaks service-to-service calls; these are shared secrets, not per-caller. |
| `msg91-auth-key-{env}` | Yes | Vendor credential; cannot be regenerated by us. |
| Drive OAuth client id / secret / refresh token | **Cannot carry over — see §4** | |
| `create-app-rt-role-sql`, `seed-full-sql`, `seed-superadmin-sql`, `diag-sql` | Yes | Operational SQL held as secrets. |

**Transfer them through the approved secret-transfer ceremony** — never through files, logs, shell history,
GitHub output, or migration evidence.

### 3.1 The database roles the dump will not carry

`gcloud sql export sql` produces a `pg_dump` of the **database**. It does **not** include instance-level
PostgreSQL roles. `app_rt` and `appuser` therefore do not exist in the destination until you create them:

1. create the instance, then create `appuser` with the value of `db-password-prod`;
2. import the dump;
3. run `scripts/create-app-rt-role.sql` (via the `ims-app-rt-prod` Cloud Run job pattern) with
   `app_rt_password` = the value of `app-rt-password-prod`. The script creates `app_rt` as
   `LOGIN NOINHERIT NOCREATEROLE NOCREATEDB **NOBYPASSRLS**` and grants schema usage.

Miss step 3 and every service fails to connect, with RLS behaviour that will not reproduce in tests —
`app_rt` is the RLS-subject role while `appuser` is RLS-exempt.

## 4. Drive photo import — the one hard blocker

The OAuth client behind Drive photo import is owned by **`custoking`** (confirmed from the client ID's
project-number prefix on both dev and prod secrets). **OAuth clients cannot be moved between projects.**
Deleting `custoking` therefore breaks photo import permanently unless it is rebuilt first.

What survives and what does not:

- **Drive folders survive.** They belong to a Google *account*, not to the project, so
  `STUDENT_PHOTO_IMPORT_DRIVE_ROOT_FOLDER_ID` and the 7 rows in `student.photo_import_drive_folders` stay
  valid.
- **The client, its secret, and the refresh token do not.** A new consent screen and client must be created
  in the destination organization, and the same operator must re-consent to mint a fresh refresh token.

One useful piece of evidence: the production refresh token was created **2026-08-02** and still works 16
days later. Testing-mode refresh tokens expire after 7 days, so the existing consent screen is **published,
not in Testing**. Expect the replacement to need the same publishing status — and if the granted scope is a
restricted Drive scope, Google verification applies and can take **weeks**.

**Start this first.** It is the only item on the critical path whose duration is outside your control.

## 5. What is destroyed with the project and cannot be recovered

| Asset | Consequence | Mitigation before deletion |
| --- | --- | --- |
| **Cloud Run URLs** (`*.a.run.app`) | Permanently stop resolving. **There is no custom domain**, so every bookmark and any shared link breaks with no redirect possible. | See §6 — this is the biggest end-user risk. |
| **Drive OAuth client** | Photo import dies | §4 |
| **`_Required` log bucket** — 400-day retention, **locked** | The admin-activity/audit trail dies with the project. Locking prevents early deletion but not project deletion. | Export the audit log to a destination sink or archive if any retention obligation exists |
| **`custoking-compliance-india`** — 180-day India-resident logs, **not locked** | 180 days of compliance logs die | Export before deletion if required |
| **Cloud SQL backups and PITR** | All 14 retained backups plus the 7-day transaction-log window die. **No post-deletion restore is possible.** | Do not delete until the destination has its own proven backup + independent restore drill |
| **BigQuery `billing_export`** | All historical cost data dies | Export the tables if cost history matters |
| **Artifact Registry** | 244 images / ~12 GB and all release history die; only copied digests survive | Copy the 7 live digests; decide consciously about history |
| **Monitoring, uptime, trace history** | All observability history dies | Accept, or export dashboards |
| **Project ID `custoking`** | Reserved permanently by Google after deletion; **can never be reused** | Accept |
| **WIF pool / service accounts / secrets** | Die; already planned to be rebuilt | §3 |

Deletion puts the project in a ~30-day recoverable pending state before it becomes permanent. **Treat that
window as the real safety net**, and do not begin it until the destination has passed a full restore drill.

## 6. The end-user continuity problem

There is no custom domain and no DNS layer. Today users reach production at a
`custoking-frontend-prod-<hash>.a.run.app` hostname. After migration the hostname changes; after deletion
the old one dies with no redirect.

Options, in order of preference:

1. **Introduce a custom domain before cutover** and point it at the new production frontend. This makes
   this migration — and every future one — a DNS change, and permanently removes the class of problem.
   Two mechanisms: a Cloud Run **domain mapping** (simplest, but regional availability must be confirmed
   for `asia-south2` before relying on it), or a **global external Application Load Balancer with a
   serverless NEG** (works in any region, but adds a forwarding-rule cost of roughly ₹1,500–2,000/month).
2. **Run both environments in parallel and communicate the new URL**, keeping the source alive through a
   notice period. Costs the duplicate-prod-database rate of ~₹104/day.
3. Switch and announce. Cheapest, and the only option with no safety margin.

Note the deterministic URL form `<service>-<PROJECT_NUMBER>.<region>.run.app` is available in the
destination, so the new URLs can be published **before** anything is deployed.

## 7. Services and configuration — what needs no work

Verified, so it does not consume migration effort:

- **No application code changes.** All GCP config is environment-variable injected.
- **MSG91 is not live in production.** `MSG91_DRY_RUN=true` and
  `NOTIFICATION_DELIVERY_PROVIDER=logging` on the running prod service. All four MSG91 endpoints are
  **outbound-only** — there is no inbound webhook or callback URL to re-register, and no IP allowlist
  (the static-egress script was never applied: no Cloud Router, no NAT, no reserved external IP).
- **No inbound external integrations at all** were found in service configuration.
- **Durable events are fully drained** — 0 pending and 0 dead across all three outboxes, inbox 100%
  `PROCESSED`. Nothing is in flight to lose.
- **Schema state matches the repository exactly** — every schema is Flyway baseline + repo count.

## 8. Ordered plan to deletion

1. **Recreate the Drive OAuth client** in the destination organization; re-consent; confirm publishing
   status and scope. Longest lead time — start now.
2. Clear the billing-account blocker (B1) so destination budgets and alerts can exist.
3. Decide the custom-domain question (§6). If yes, provision it before cutover.
4. Build `custoking-dev`; transfer secret values; create `appuser` and run the `app_rt` role script;
   import data; run the full ledger and compare.
5. Repair the two pre-existing data defects (`dim_student` off-by-one; 28 dead objects) so the destination
   ledger is unambiguous.
6. Build `custoking-prod` from the accepted dev procedure. Prove backups, PITR, and an **independent
   restore drill** on the destination.
7. Cut over. Keep `custoking` intact and running for the agreed notice period.
8. Export audit, compliance, and billing-export data that must outlive the project.
9. **Only then** begin deletion, and treat the ~30-day pending window as the final safety net.

## 9. Verification gates added by the deletion premise

| Gate | Why |
| --- | --- |
| A Drive photo import completes end-to-end in the destination using a newly minted refresh token | The only unrecoverable dependency |
| An existing user signs in with their **existing** password against the destination | Proves the BCrypt hashes and identity data survived |
| A scoped-role user (SCHOOL_ADMIN or TEACHER) exercises a school-scoped action | Proves `user_role_assignments` and RLS scoping survived; the coarse `role` column alone would not catch this |
| `app_rt` exists on the destination with `NOBYPASSRLS`, and a tenant-scoped read returns correctly filtered rows | Proves step 3 of §3.1 ran and RLS is live |
| An independent restore drill succeeds **on the destination** | After deletion this is the only recovery path |
| Audit, compliance, and billing-export data required to outlive the project has been exported | Locked log buckets still die with the project |
| The production URL a user visits today resolves to the new environment, or the change has been communicated and accepted | No DNS layer exists to absorb this |
