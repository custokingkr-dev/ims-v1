# EMAIL callback body boundary — 2026-10-08

The accepted PR335 EMAIL receiver checked callback credentials and its32768-byte limit inside a handler with `@RequestBody byte[]`. Spring7.0.9 resolves that argument before invoking the handler and reads the advertised body or reads to EOF. A caller already authorized to invoke the private Cloud Run service could therefore consume body-buffering resources before callback authentication. [Exact dated source/dependency/primary review](acceptance-callback-body-primary-review.json), [Spring converter source](https://raw.githubusercontent.com/spring-projects/spring-framework/v7.0.9/spring-web/src/main/java/org/springframework/http/converter/ByteArrayHttpMessageConverter.java), [handler invocation source](https://raw.githubusercontent.com/spring-projects/spring-framework/v7.0.9/spring-web/src/main/java/org/springframework/web/method/support/InvocableHandlerMethod.java).

The existing public gateway already enforces32768 actual bytes for this exact callback route and has rate/deadline controls. Saved direct anonymous and forged requests to the private service returned403. This finding concerns authenticated direct invocation; no public unbounded exploit, measured exhaustion or production outage was reproduced. Cloud Run's documented HTTP/1 request quota is32MiB, which does not implement this application32KiB allowance. Tomcat's `maxPostSize` limits form-parameter parsing and does not impose a general JSON limit. [Cloud Run quotas](https://docs.cloud.google.com/run/quotas), [Tomcat HTTP configuration](https://tomcat.apache.org/tomcat-11.0-doc/config/http.html).

The forward fix authenticates both existing credentials before inspecting length, acquiring the servlet stream or starting asynchronous processing. A separate EMAIL reader then counts at most32769 bytes, rejects oversize bodies, permits two admitted operations and applies a five-second read deadline. The existing generic reader retains its8192-byte allowance and existing responses. Strict UTF-8 decoding precedes duplicate/trailing-token JSON rejection and the unchanged report schema/bindings; an existing UTF-8 BOM remains accepted, while UTF-16/32 and malformed UTF-8 are rejected. [RFC8259 section8.1](https://www.rfc-editor.org/rfc/rfc8259.html#section-8.1) requires UTF-8 for network JSON between systems. Ordinary receipt processing still works when the live-send gate is disabled; this fix does not enable live sending or normalized report admission.

Independent review also found lifecycle hazards in the shared reader: setup failures could strand capacity, and a disconnected response could release a processing slot while its owned-byte action was still executing. The fix releases each permit once, preserves servlet-stream isolation and retains action ownership until processing ends. An explicit five-second EMAIL Spring transaction/JDBC timeout bounds selected database waiting separately from the body timer, which ends after the bytes are owned. Existing connection acquisition and external driver cancellation do not receive a new five-second whole-operation guarantee.
