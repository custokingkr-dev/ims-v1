# Generic MSG91 inbox safety

This source follow-up does not enable MSG91, send a message, or establish live provider delivery acceptance. The existing `MSG91_DRY_RUN=false` startup and send rejection remain in place. Logging and MSG91 dry-run retain their existing processing contract.

For a future reviewed live generic adapter, `NotificationInboxProcessor` delegates to `GenericNotificationSubmissionWorker`. Current producer evidence must first pass the existing admitted source/type/template/purpose/consent/destination/freshness checks. The worker additionally resolves current ownership, primary guardian, consent and preference through school-core. It suppresses unavailable, denied, incomplete, changed-recipient or stale owner evidence before reserving or submitting. Fee reminders use the explicit SMS fee-reminder endpoint. School notices use the notice endpoint. Absentee alerts use the dedicated absentee endpoint and bind the source notification ID, attendance date, exact message SHA-256 and source event ID; they cannot borrow another purpose's endpoint.

`V15__generic_submission_reservations.sql` creates a tenant-scoped, FORCE-RLS ledger. One stable event ID can reserve one immutable request SHA-256. Runtime ACLs permit SELECT/INSERT and updates of outcome/timestamp only; they prohibit deleting the reservation or changing its binding. The existing owner migration callback copies that bounded ACL to the dedicated platform runtime role. A changed request or foreign-school event collision fails closed.

The worker suspends the surrounding transaction and commits the ledger reservation, inbox `SUBMITTING`, and audit attempt in a separate transaction before provider I/O. It rechecks current owner evidence after reservation immediately before I/O. A second concurrent worker cannot reserve the event. A process failure or lost outcome commit leaves `SUBMITTING`, which cannot be automatically resent. An exception, timeout, revoked second policy check, missing/mismatched receipt, or legacy `void` provider return becomes `UNKNOWN`. A request-bound typed result can become `ACCEPTED` or `REJECTED`; `ACCEPTED` is never mapped to `PROCESSED` or `DELIVERED`. None of these states is retryable. A SQL trigger rejects a stale command's attempt to reset them or replace their payload. Student erasure can still move them to terminal `SUPPRESSED` and redact their payload; worker completion does not overwrite that suppression.

The synchronous delivery answer exposes `SUBMITTING`, `UNKNOWN`, `ACCEPTED` and `REJECTED` explicitly. Owner callers must retain them as terminal submission/reconciliation states and refrain from automatic resend. There is deliberately no reset/delete/resume API for the ledger. An operator must not replace the stable event ID to bypass uncertainty. `V16` persists the bounded provider request ID, correlation ID and sanitized result reason, and prevents any final result from being downgraded or rewritten. The typed result binds the event ID, stable correlation ID and a SHA-256 over length-prefixed provider-facing request fields. A reply for another event, template, recipient or payload cannot mark the reservation accepted.

## Prepared provider result adapter

`NotificationDeliveryProvider.submit` is backward compatible: an existing void adapter still performs one attempt, but both a void return and an exception produce `UNKNOWN`. The public MSG91 typed entry point retains the unconditional live-admission rejection, including direct calls outside Spring. Its prepared transport is fixed to the official HTTPS SMS flow endpoint, disables redirects, limits the body/response, bounds concurrency, and uses the existing single-use publisher and complete-response deadline. It makes no automatic retry.

The narrow SMS codec accepts HTTP200 only with the documented `type=success` and 24-hex `message` request ID. It recognizes only the documented missing-flow error as definite rejection; a generic HTTP4xx alone is insufficient. Unknown HTTP outcomes, timeouts, interrupted/oversized/malformed responses, missing IDs, contradictory fields and mismatched echoed correlation remain `UNKNOWN`. The [official SMS FLOW sample](https://api.msg91.com/apidoc/textsms/send-sms-flow.php) documents those response fields. This published sample uses a legacy `flow_id` request; the existing body builder uses `template_id`, so the selected current template/API version still needs controlled provider acceptance before admission. No assumption is made that a correlation ID deduplicates vendor requests.

EMAIL and WhatsApp generic response decoding currently fail closed with `UNKNOWN`. The public documentation overview did not expose a verifiable channel response schema through accessible endpoint references during this review; an existing broadcast sample is not silently promoted into a generic receipt contract. The existing authenticated EMAIL broadcast report endpoint remains restricted to its broadcast ledger. Generic acceptance does not reuse that endpoint or invent SMS/WhatsApp delivery reports. MSG91 also explicitly distinguishes [API acknowledgement from actual email delivery](https://msg91.com/help/transactional-email/how-to-check-transactional-email-delivery-report).

## Verification and remaining acceptance

Focused unit tests exercise owner unavailability, denial, changed guardian/destination, expired evidence, revocation between reservation and I/O, no active transaction during I/O, and terminal uncertainty. PostgreSQL integration tests load the actual notification migrations and use a non-superuser, non-bypass runtime role. They exercise one-winner concurrency, lost result transaction, changed bindings, foreign-school invisibility, denied reservation DELETE, stale inbox reset rejection, erasure suppression, and independent-connection visibility of the committed reservation before the worker invokes a controlled provider stub. No external provider is contacted.

Local verification on 2026-10-07: full platform suite **402 passed, zero skipped**, including **five actual PostgreSQL integration cases**; after adding three final routing/terminal-state assertions, the final focused policy/worker/processor/command run **24 passed, zero skipped**. These overlapping runs are not additive test totals. Package-shape and runtime-schema dependency baseline audits passed. The current-owner absentee binding test uses a controlled owner response; actual owner repository/controller coverage is a separate coordinated school-core change.

The subsequent typed-result implementation passed the full platform suite **417/417, zero skipped**. Its final focused run after wiring the unconditional MSG91 admission guard passed **40/40, zero skipped**, including **six actual PostgreSQL cases** and **six codec/transport cases**, with real loopback HTTP acceptance, delayed response after server request receipt, malformed response, rejection, oversized response and redirect checks. These local endpoints use synthetic credentials and destinations; no vendor request was made. The additional PostgreSQL case proves persisted request/correlation IDs, no retry after acceptance, immutable final receipt evidence and erasure suppression. The earlier 402-test/24-test figures above are implementation checkpoints, not current aggregate totals.

This is an application reservation, not a promise that MSG91 deduplicates `CRQID`. It trades automatic retries for possible non-delivery when the process stops between reservation and submission. Cross-service owner checks are bounded fresh observations; they do not provide a distributed lock against consent changes after the final check. Live admission still requires the selected current provider/template contract, authenticated status reconciliation and real controlled owner-policy/provider acceptance exercises. Generic EMAIL/WhatsApp channel receipt contracts are also still unverified. Provider credentials alone cannot satisfy those requirements. Do not claim vendor delivery, physical recipient receipt, or operational reconciliation from these local tests.
