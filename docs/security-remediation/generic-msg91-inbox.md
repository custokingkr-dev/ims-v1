# Generic MSG91 inbox safety

This source follow-up does not enable MSG91, send a message, or establish live provider delivery acceptance. The existing `MSG91_DRY_RUN=false` startup and send rejection remain in place. Logging and MSG91 dry-run retain their existing processing contract.

For a future reviewed live generic adapter, `NotificationInboxProcessor` delegates to `GenericNotificationSubmissionWorker`. Current producer evidence must first pass the existing admitted source/type/template/purpose/consent/destination/freshness checks. The worker additionally resolves current ownership, primary guardian, consent and preference through school-core. It suppresses unavailable, denied, incomplete, changed-recipient or stale owner evidence before reserving or submitting. Fee reminders use the explicit SMS fee-reminder endpoint. School notices use the notice endpoint. Absentee alerts use the dedicated absentee endpoint and bind the source notification ID, attendance date, exact message SHA-256 and source event ID; they cannot borrow another purpose's endpoint.

`V15__generic_submission_reservations.sql` creates a tenant-scoped, FORCE-RLS ledger. One stable event ID can reserve one immutable request SHA-256. Runtime ACLs permit SELECT/INSERT and updates of outcome/timestamp only; they prohibit deleting the reservation or changing its binding. The existing owner migration callback copies that bounded ACL to the dedicated platform runtime role. A changed request or foreign-school event collision fails closed.

The worker suspends the surrounding transaction and commits the ledger reservation, inbox `SUBMITTING`, and audit attempt in a separate transaction before provider I/O. It rechecks current owner evidence after reservation immediately before I/O. A second concurrent worker cannot reserve the event. A process failure or lost outcome commit leaves `SUBMITTING`, which cannot be automatically resent. An exception, timeout, revoked second policy check, missing/mismatched receipt, or legacy `void` provider return becomes `UNKNOWN`. A request-bound typed result can become `ACCEPTED` or `REJECTED`; `ACCEPTED` is never mapped to `PROCESSED` or `DELIVERED`. None of these states is retryable. A SQL trigger rejects a stale command's attempt to reset them or replace their payload. Student erasure can still move them to terminal `SUPPRESSED` and redact their payload; worker completion does not overwrite that suppression.

The synchronous delivery answer exposes `SUBMITTING`, `UNKNOWN`, `ACCEPTED` and `REJECTED` explicitly. Owner callers must retain them as terminal submission/reconciliation states and refrain from automatic resend. There is deliberately no reset/delete/resume API for the ledger. An operator must not replace the stable event ID to bypass uncertainty. `V16` persists the bounded provider request ID, correlation ID and sanitized result reason, and prevents any final result from being downgraded or rewritten. The typed result binds the event ID, stable correlation ID and a SHA-256 over length-prefixed provider-facing request fields. A reply for another event, template, recipient or payload cannot mark the reservation accepted.

## Prepared provider result adapter

`NotificationDeliveryProvider.submit` is backward compatible: an existing void adapter still performs one attempt, but both a void return and an exception produce `UNKNOWN`. The public MSG91 typed entry point retains the unconditional live-admission rejection, including direct calls outside Spring. Its prepared transport is fixed to the official HTTPS SMS flow endpoint, disables redirects, limits the body/response, bounds concurrency, and uses the existing single-use publisher and complete-response deadline. It makes no automatic retry.

The narrow SMS codec accepts HTTP200 only with the documented `type=success` and 24-hex `message` request ID. It recognizes only the documented missing-flow error as definite rejection; a generic HTTP4xx alone is insufficient. Unknown HTTP outcomes, timeouts, interrupted/oversized/malformed responses, missing IDs, contradictory fields and mismatched echoed correlation remain `UNKNOWN`. The [official legacy SMS FLOW sample](https://api.msg91.com/apidoc/textsms/send-sms-flow.php) documents those response fields. Fresh primary research found the [current Send SMS reference](https://docs.msg91.com/sms/send-sms), which documents `template_id` at the existing endpoint. Its response sample was not exposed consistently by the public renderer, so the legacy acknowledgement codec is not presented as the selected current account's proved response contract. The exact template/version and controlled provider acceptance remain necessary before admission. No assumption is made that a correlation ID deduplicates vendor requests.

EMAIL and WhatsApp generic submission-response decoding still fail closed with `UNKNOWN`; an existing broadcast sample is not promoted into a generic receipt contract. The existing authenticated EMAIL broadcast report endpoint remains restricted to its broadcast ledger. Fresh research found configurable report documentation, described below, but that does not supply an account-selected submission-response contract or activate a raw generic webhook. MSG91 also explicitly distinguishes [API acknowledgement from actual email delivery](https://msg91.com/help/transactional-email/how-to-check-transactional-email-delivery-report).

## Disabled internal normalized reconciliation

This follow-up adds source for `POST /api/v1/internal/notifications/reports/reconcile`. It is an internal trusted operator boundary, not a public vendor callback. The gateway does not expose it. Application and deployment defaults leave `NOTIFICATION_REPORT_RECONCILIATION_ENABLED=false`, `NOTIFICATION_REPORT_RECONCILIATION_TOKEN` blank and `NOTIFICATION_REPORT_CALLER_SERVICE_ACCOUNTS` absent/blank. Enabling it requires an explicitly governed purpose identity and dedicated secret; no IAM, secret, provider or live configuration was changed by this source work.

Both the guarded machine filter and controller require the exact report caller's signed OIDC identity. The controller additionally checks the dedicated `X-Notification-Report-Token` with constant-time comparison and the exact `notification:report-reconcile` purpose. A secret shorter than 32 UTF-8 bytes, the shared notification/delivery credential, the provider credential, an empty caller set, or a caller set overlapping gateway/user-carrier or delivery callers is refused. Forwarded user authority and query parameters are refused. Disabled, missing or mismatched configuration cannot fall back to shared-token-only admission.

Version 1 accepts exactly nine JSON fields: `version`, `schoolId`, `eventId`, `requestSha256`, `correlationId`, `providerRequestId`, `status`, `occurredAt` and `evidenceSha256`. Duplicate/unknown fields, trailing JSON, string/coerced school IDs and unsupported statuses fail. Status is one of `ACCEPTED`, `DELIVERED`, `DELIVERY_FAILED`. The timestamp uses an explicit offset and no finer than PostgreSQL microsecond precision. The canonical report hash length-prefixes all fields and normalizes time to UTC. Raw destinations, sender addresses, payloads, provider reasons and secret values are never accepted or persisted by this boundary. The evidence SHA is an operator assertion about reviewed evidence, not proof of a vendor signature or possession of a recipient device.

Only an existing `ACCEPTED` reservation with the exact school, event, immutable request SHA, deterministic correlation and already saved provider ID can be reconciled. The inbox must also be `ACCEPTED`; foreign, missing, suppressed, mismatched, stale or future reports receive the same acknowledgement without changing evidence. The repository uses the claimed school's tenant scope with bypass off; it performs no cross-tenant discovery. `UNKNOWN`, `SUBMITTING` and `REJECTED` stay quarantined. A report with a newly supplied provider ID cannot establish lost-response acceptance, reset the original submission, create a reservation or cause a retry/resend.

`V17` adds minimal append-only `generic_delivery_reports` and separate `generic_delivery_results`. Exact foreign keys bind result identity to the receipt. Runtime grants exclude report UPDATE/DELETE, result identity UPDATE, and caller-supplied receipt timestamps; broad owner defaults are explicitly revoked before bounded column grants, and the dedicated-role callback retains those grants. Delivery state cannot downgrade; contrary terminal reports or changed normalization of the same evidence make it permanently `REPORT_CONFLICT`. A direct runtime `DELIVERED`/`DELIVERY_FAILED` update requires matching appended evidence. This state never promotes the original inbox/submission outcome or claims recipient receipt.

Reconciliation locks the inbox before result state. An invoker-privilege trigger suppresses a result when the inbox is erased, including changes made by the existing payload-redaction trigger. Erasure committed first prevents a result; erasure committed after a report atomically moves its result to terminal `SUPPRESSED`. Late reports cannot append evidence or revive it. Required historical report evidence is retained; no retention period or physical purge policy is invented.

The actual Servlet `AsyncContext`/nonblocking `ReadListener` owns body reading. It reads only while ready and active, caps input at 8 KiB, admits two active bodies and enforces a five-second monotonic body deadline. Timeout completes the context before late callbacks can read or parse a recycled stream. Processing receives a private byte array after the body completes; its separate ten-second transaction uses five-second statement and two-second lock limits. A lost HTTP acknowledgement can be safely retried as a report replay, never as a send.

## Current primary report documentation and selected configuration

The read-only dev service observation during this work still selected `NOTIFICATION_DELIVERY_PROVIDER=logging`, `MSG91_DRY_RUN=true` and `BROADCAST_LIVE_ENABLED=false`. SMS flow, EMAIL sender/domain and WhatsApp integrated-number environment entries were absent; secret references were observed without reading values. This does not inventory per-school sender profiles or prove that the vendor account has no templates. It establishes that no live generic channel contract was selected by the inspected service configuration.

The [current SMS webhook guidance](https://msg91.com/help/webhooks/how-can-i-get-the-delivery-reports-on-my-webhook-url) defines distinct v2 form, v3 JSON and v4 report shapes, numeric statuses and `CRQID`. It requires selecting a version in the account. The [new EMAIL webhook guidance](https://msg91.com/help/webhook-new/how-to-receive-email-delivery-reports-via-webhook-new/) documents customizable JSON fields, event status IDs and custom headers; some `requestId`/`uuid` descriptions conflict with its sample. The [new WhatsApp guidance](https://msg91.com/help/webhook-new/how-to-receive-whatsapp-delivery-reports-via-webhook-new) documents customizable outbound fields, `crqid`, request/message IDs, timestamps, custom headers and duplicate events. These primary sources support preparation and explicit owner configuration; they do not prove which shape, authentication header, account identity or identifier semantics is configured here. No automatic raw-vendor codec or webhook is enabled from a common sample.

Live generic admission still needs exact account-selected send/response/report schemas, configured authentication and report binding, approved templates/senders/recipients and controlled provider acceptance. Lost-response attestation for a missing provider ID remains a separate unimplemented contract. This internal source boundary does not close those criteria or weaken the existing live-send rejection.
