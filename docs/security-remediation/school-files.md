## Existing object cache rollout

Run PhotoCacheMetadataMigration with the service's resolved dependency classpath and configured private bucket. First invoke `com.custoking.ims.schoolcoreservice.infrastructure.PhotoCacheMetadataMigration BUCKET` (dry-run); save candidate count. Invoke with `BUCKET --apply`, save updated count, then rerun dry-run and require zero candidates. The utility prints counts rather than sensitive object names, filters only student photo objects, and preserves content/ACL/generation while using metageneration matching. Concurrent metadata update failure stops the operation; retry after reviewing the cause. Do not restore the historical public-cache header during application rollback.

Verify representative existing and new objects using authorized signed fetches: Cache-Control private,no-store; unsigned fetch denied; signed capability expiry enforced; photo proxy no-store and browser cache behavior recorded. Inspect bucket IAM/public-access prevention, soft-delete/version retention, CDN/cache configuration separately. The utility does not erase previously downloaded browser copies.

## Retention and deletion operation

Keep the existing documented fourteen-day temporary photo-import source lifecycle; inspect actual bucket lifecycle configuration and legacy cleanup dry-run before deleting. Originals retained in external Drive remain subject to that owner's permissions and recorded access-revocation workflow; bucket deletion alone does not delete them. Student photos follow the existing committed permanent student deletion and retryable object cleanup. Run a controlled student deletion drill tracing database row, guardian/consent and import-row references, active photos and old content-addressed versions, temporary originals, reporting tombstones, outbox/inbox, exported archives, backup/PITR and audit evidence.

Business/import evidence, exports, audit records, backups/PITR and storage soft-delete each require an explicit owner-approved retention schedule; no arbitrary legal retention duration is introduced here. Record store, purpose, access owner, retention period, cleanup job, deletion exception and restore handling. Backups restored after deletion must replay the deletion ledger/tombstones before becoming accessible. Document proof of retrying failed object deletion without resurrecting the student, and the distinction between removed access and downloaded copies. These operational approvals/drills are required before SEC-30 closure.

## Rollback

Code rollback can restore previous parsing behavior, but must not restore unsafe cache metadata, remove V36 migration history, decrement student versions or weaken private-address guards. Existing migrations are unchanged. Keep V36 column/trigger after application rollback; old producers omit version and platform compatibility rejects their legacy snapshots after a versioned state is established. A sustained rollback therefore needs the coordinated platform recovery/backfill plan. Import limits may reject formerly accepted complex/formula files: convert formulas to values and split oversized files; never bypass parser guards.

## Research used

The connection-bound resolver uses Apache's supported [DnsResolver contract](https://hc.apache.org/httpcomponents-client-5.6.x/current/httpclient5/apidocs/org/apache/hc/client5/http/DnsResolver.html). Google documents object metadata and the distinction between private caches and no-store in [Cloud Storage caching](https://docs.cloud.google.com/storage/docs/caching); that distinction motivates both existing-object metadata migration and explicit browser verification. The export policy follows the dangerous prefixes and consumer caveats described in [OWASP CSV injection](https://community.owasp.org/attacks/CSV_Injection). These references explain design choices; they do not replace the controlled tests or deployed configuration evidence.
