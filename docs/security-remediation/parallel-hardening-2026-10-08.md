## Provider wire ambiguity

The injected general application JSON mapper could accept duplicate fields or trailing JSON when interpreting SMS acknowledgements, prepared SMS bodies and EMAIL acknowledgements. UTF-8 replacement could also manufacture a different response text. Four new regressions failed on the old source. Provider wire parsing now uses an independent strict duplicate/trailing-token mapper; bounded transport decoding rejects malformed UTF-8 while retaining valid multibyte chunk support. The existing EMAIL report receiver also uses a strict byte parser and rejects ambiguous input before any ledger write. Provider payload builders reject duplicate/trailing data across SMS/OTP/EMAIL/WhatsApp, with ordinary channel controls retained. Ambiguous responses become `UNKNOWN`, and ambiguous prepared bodies are rejected before I/O. Existing reservation and no-resend controls continue to apply.

EMAIL no longer treats undocumented HTTP400/405/413/415 or HTTP402 as definitive rejection. Existing documented HTTP401/403/404/422 rejection handling requires a strict single object and rejects contradictory acknowledgement fields. A recognizable queue identifier, success status, false/nonboolean error flag or ambiguous data cannot bypass uncertainty by arriving with a rejection status. This uses the selected existing submission boundary and [MSG91's published HTTP error meanings](https://msg91.com/help/email/email-rejection-types-and-error-codes); it adds no account authentication, recipient scope or delivery attestation. An API acceptance still does not prove delivery or recipient receipt.
