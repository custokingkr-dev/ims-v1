# External erasure journal and isolated restore replay prototype

The new [dev toolkit](../../scripts/security/dev-erasure-journal.py) generates reviewed read-only export SQL, canonical terminal-event journal objects, create-only GCS request plans and exact synthetic clone replay SQL. It makes no network connection, SQL execution, cloud mutation, upload, restoration-ready assertion or delivery-resume decision. No source application deletion contract was changed. This is useful executable plan generation and locally tested SQL; it is **not** an operationally deployed durable journal or a production restore gate.

## Current gap

`StudentReadRepository.deleteStudent` locks a student, validates admission confirmation, removes its source/child records and writes `StudentDeleted:<id>` to `tenant_school.outbox_events` in the same transaction. `deletePhotosAfterCommit` retains photo keys only in process memory; `StudentPhotoStorage.deleteStoredPhoto` catches/logs storage deletion failures. Platform `ReportingEventInboxProcessor` atomically processes the deletion into `DimensionProjectionRepository` terminal tombstones and removes its projections. All those SQL rows can be rewound together by an older Cloud SQL recovery snapshot.

Mirroring **committed** outbox records into independently managed storage protects the mirrored history from SQL rollback. It does not eliminate the SQL commit → external mirror crash gap. A process crash or recovery before the external write can still lose a successful erasure's intent. Periodic exports, Pub/Sub retention, current SQL tombstones and a snapshot test cannot establish precommit durability. That acceptance criterion remains open.

A genuine precommit design needs an explicit irreversible deletion-request contract: validate tenant/permission/fresh step-up/confirmation, durably claim an immutable external intent, then execute/retry source erasure and downstream fences; a SQL rollback after the external claim cannot silently cancel that authorized intent. A202/status/idempotent-retry contract should be reviewed before implementing this semantic change. No such authorization/contract was invented here.

## Scope and operation sequence

The prototype accepts only project `custoking-dev`, original instance `custoking-db-dev`, database `custoking_dev`, marker `SEC-ACPT-20261007` and the exact twenty approved student/school mappings990007301..990007320. The inventory includes an independently reviewed ownership-proof SHA256 and an external source-lineage identifier. It rejects arbitrary IDs, schools, tables, projects and free-form SQL. All input JSON is limited to128KiB. UTC capture/clone evidence must be fresh within10minutes. Reviewed inventory, journal and clone evidence hashes are mandatory. Output files are exclusively created, never overwritten.

These source names were checked against [successful isolated PITR evidence](dev-pitr-20261007095108-6f59ef96.json) and `PGDATABASE=custoking_dev` in [the PITR job generator](../../scripts/invoke-dev-schema-only-pitr-drill.ps1). Clone isolation/provenance fields supplied to this tool remain reviewed caller evidence, not an independent live verification by the generator.

1. Prepare the reviewed inventory from existing sanitized fixture ownership evidence; do not derive arbitrary deletion scope from a restored user request. SHA256 uses canonical JSON: sorted keys, compact ASCII JSON plus one LF.
2. `export-sql` generates `BEGIN READ ONLY` SQL for the fixed source outbox scope. It includes published and unpublished terminal records and does not filter by `occurred_at`: transaction-start timestamps and SQL sequence IDs are not commit-order watermarks. Run only through a separately reviewed, time-bounded read-only source transport.
3. `seal` requires one valid terminal event per reviewed student, exact event key/aggregate/school binding, unique source event IDs and timestamps not later than capture. Unexpected record fields, PII, missing records, corrupted hashes and stale captures fail. Coverage explicitly means these20 targets; `globalJournalComplete=false`, `precommitDurabilityGuaranteed=false`.
4. `storage-plan` generates only fixed `https://storage.googleapis.com` requests into `custoking-dev-erasure-journal/synthetic/<reviewed-lineage>/...`. Each terminal record has a stable identity key and `ifGenerationMatch=0`. The content-addressed manifest changes for a new coverage capture, while identical event objects retain stable keys. On412, an operator must read the existing exact object generation and compare the complete canonical payload SHA256; mismatch stops. After create/readback, record its bucket/object/generation/size/hash and consume only a generation-pinned read. No upload happens in this tool.
5. `replay-sql` requires a reviewed exact nonce clone name `custoking-dev-security-restore-YYYYMMDDHHMMSS-xxxxxxxx`, matching external lineage, RUNNABLE state, a private non-primary/non-loopback IP, detached traffic and disabled delivery. Source IP10.92.0.3 is rejected. The reviewed transport must independently prove that its connection points to that clone; a SQL comment alone cannot bind a physical connection. This prototype deliberately supplies no executor.
6. The generated transaction checks restored marker/admission/created-by/school ownership, seeds20 terminal platform tombstones with original deletion timestamps, fences the exact queued recipient rows and removes exact projections before source rows. Different school bindings or unexpected photos/guardian/financial/attendance/import/review/enrollment/consent children abort rather than pretending to implement a broad business erasure. Atomic rollback preserves everything on failure. It is idempotent for already-absent matching synthetic rows. A real restore must call the complete owner erasure workflow for dependent records, preserve required financial/audit evidence under an approved policy, and separately address object/provider copies.

Every mode continues to report `restorationReady=false` and `deliveryResume=false`. Replay success is necessary evidence, never sufficient authority to attach traffic or resume any Scheduler/Pub/Sub/provider worker.

## Managed storage and caller isolation still to provision

Use a dedicated journal bucket outside SQL backups and outside student-photo/dashboard state storage. Public access prevention and uniform bucket-level access are required. A dedicated exporter should read only source deletion evidence and write only its reviewed journal prefix; minimal bucket permissions are `storage.objects.create` plus `storage.objects.get` for conflict verification, with no update/delete permission. The restore reader needs generation-pinned get for approved objects and no write/delete; delivery runtimes need neither journal administration nor owner SQL credentials. A separate controlled operator owns coverage manifests and restore approvals. No bucket, IAM grant, scheduled export or retention lock was created by this task.

[GCS generation0 preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions) support create-only requests, and [successful writes are strongly consistent](https://docs.cloud.google.com/storage/docs/consistency). IAM must enforce that runtime writers cannot replace/delete existing objects; an application precondition alone is insufficient against a compromised credential. Lifecycle deletion would undermine the journal unless its horizon is explicitly reconciled with every retained recovery copy. No retention period, RPO or RTO was assumed. [Bucket Lock cannot be reduced or removed once locked](https://docs.cloud.google.com/storage/docs/bucket-lock); do not irreversibly lock an invented policy.

## Production implementation boundaries

The smallest future application changes are an external `ErasureJournal` adapter under school-core infrastructure, an owner `StudentErasureService` separating validated intent claim from transactional erasure, stable student incarnation/lineage and a local progress table, and a durable photo cleanup queue replacing the after-commit memory callback. A migration can store local journal generation/digest/phase and object generations but cannot itself make intent survive an earlier SQL restore. Restores predating any incarnation migration must stay quarantined unless an approved legacy ownership fingerprint can be proved; never delete a newly reused student ID on identifier equality alone.

Platform replay should reuse `DimensionProjectionRepository.deleteStudent` terminal locking/fences, extend it to cancel pending broadcast/notification work for the scoped student, and recheck source/restore fence before every provider attempt. Current workers already fetch fresh owner consent/policy; restoration can also restore old owner consent, so owner freshness alone does not replace an external erasure fence. Existing inbox dedupe/tombstones must be seeded before old upserts or notification inbox work is processed. Provider acceptance/cancellation/deletion and object generation/version/soft-delete retention remain separate receipts, not database deletion claims.

Current source migrations `reporting/V34__student_inbox_erasure.sql` and `notification/V14__student_inbox_erasure.sql` install inbox redaction/suppression and student-fact terminal guards, including the shared student advisory lock. A real clone must have these reviewed migrations and trigger definitions verified before replay/cutover. This generator does not apply or inspect them, and its minimal PostgreSQL fixtures do not exercise those triggers. Therefore it makes no claim that all restored inbox PII was redacted or that production delivery can resume.

A real restore barrier must freeze new writes/erasures and delivery, drain in-flight work, capture complete external coverage, replay source+platform+object/provider fences, and record a new externally held restore epoch and pinned coverage generations before a controlled cutover. Do not trust a `REPLAY_COMPLETE` row restored from SQL itself. If source erasures continue concurrently, the design needs transactionally durable external sequence/coverage bookkeeping or another reviewed catch-up barrier; repeatedly reading max SQL ID/timestamp does not prove there are no gaps. The current synthetic20-target manifest cannot authorize full business restoration or automatic delivery resumption.

## Verification

`python -m unittest scripts.tests.dev_erasure_journal_test -v` runs6 controlled tests and4 actual local PostgreSQL16 tests. Controlled tests cover corruption/scope/duplicate/PII/freshness/size rejection, stable create-only object identities, no resume claim and `python -O` retaining guards. PostgreSQL tests execute source export and replay SQL, seal published/unpublished records, prove exact restored rows removed while unrelated rows remain, terminal fences persist on duplicate replay, and wrong-school or dependent financial records roll back every fence/delete. The local fixture uses minimal tables matching referenced columns; it is not a live Cloud SQL restore or a complete production-migration erasure test. No cloud mutation or business-row operation was performed.
