# Focused outbound and upload follow-up — 2026-10-07

This follow-up closes concrete gaps found after the earlier media hardening. It does not replace the earlier evidence or claim network egress enforcement has been deployed.

## Implemented

`GoogleDrivePhotoImportClient.listFiles` previously accumulated every page without a file/page ceiling; metadata GET/POST responses used unbounded `BodyHandlers.ofString`. The client now defaults to 5,000 files, 20 pages and a 60-second scan deadline, with ceilings of 20,000 files, 100 pages and 120 seconds. Repeated page tokens are rejected. Two scans and eight JSON requests are admitted per process. JSON responses use the existing bounded streaming subscriber, default 2 MiB and ceiling 8 MiB; an asynchronous request has a complete-response deadline of 30 seconds, constrained further by the remaining scan deadline. Timeout cancels the native request and releases admission. Credential acquisition remains handled by the Google credential SDK; this report does not certify its separate refresh transport deadline.

Configuration properties are `student.photo-import.drive.max-listed-files`, `max-list-pages`, `json-max-bytes`, and `list-timeout-seconds`. Runtime defaults are conservative; values outside the hard ceilings fail the attempted operation. Production Drive API origin remains the fixed official endpoint, with no configurable test origin or network guard bypass.

`ImageUrlFetcher` already validated addresses in Apache's connection resolver. Its tests previously demonstrated address rejection and a redirect to a private literal, rather than controlled DNS rebinding during connection. A package-private offline address-answer seam now tests a public preflight answer followed by a private answer in the actual Apache resolver; production HTTPS/443 and private-address restrictions remain active. Mixed public/private and NAT64-embedded private results also fail before connection.

Six focused classes ran **42 tests: 41 passed, zero failures/errors, one existing Windows symlink privilege skip**. New coverage includes four real controlled JDK HTTP cases (301-file compatibility, file/page limits, oversized GET/POST bodies, trickled response timeout with admission reuse, repeated pagination token) and two actual Apache DNS binding cases. The existing suite covers PNG/JPEG decoding, real WebP decode through the included TwelveMonkeys plugin, PDF active-content rejection on upload/legacy download, and slow image-body cancellation. No PostgreSQL test is needed for these transport-only changes. Log: `tmp/drive-ssrf-focused-tests.log`. The prior Linux symlink proof remains separate; this Windows run does not certify it.

## Remaining infrastructure preparation

The five Java manifests in `deploy/cloudrun/{identity,school-core,operations,platform,billing}-service.yaml` select `private-ranges-only`, hardcode default network/subnet, and attach no service network tags. `deploy/clouddeploy/targets-dev.yaml` supplies network/subnet parameters which those annotations do not currently interpolate. No egress firewall/NAT/Google API private route module exists in the repository Terraform inspected.

Read-only live dev metadata confirms the default asia-south2 subnet is `10.190.0.0/20`, Private Google Access is false, and the project has no explicit egress firewall rules or routers. This is current control-plane evidence, not a packet capture or proof about inherited organization policies. Public HTTPS therefore currently bypasses the configured VPC egress path. [Google Direct VPC egress documentation](https://docs.cloud.google.com/run/docs/configuring/vpc-direct-vpc) describes all-traffic routing and revision network tags; [Cloud NAT interactions](https://docs.cloud.google.com/nat/docs/nat-product-interactions) describes the additional public NAT requirements.

A safe preparatory patch can add network/subnet/tag interpolation and a disabled-by-default dev Terraform module with a dedicated subnet, Private Google Access, Google API/peer-service DNS/routes, per-service tag firewall rules, and explicit SQL TCP5432 destination allow rules. Enable it only after fresh plan/readback/connectivity probes; changing only `vpc_egress` to all-traffic can break existing APIs. An immediate tag-scoped private-range deny with exact SQL/DNS exceptions could reduce lateral movement while retaining private-ranges-only, but its effective routes/DNS and existing migration/peer behavior must be probed before apply. It would not constrain arbitrary public exfiltration.

Required destination classes are private Cloud SQL; authenticated peer `run.app` endpoints; Google credential metadata; Google APIs for GCS, IAM signing, Pub/Sub and OIDC certificates; and `www.googleapis.com` Drive plus OAuth token refresh when Drive is enabled. The platform live broadcast implementation pins `https://control.msg91.com/api/v5/email/send`; dev currently specifies logging delivery and MSG91 dry-run. SMTP host is configuration-dependent. Arbitrary **public HTTPS443 image URL imports are an implemented feature**, so a global Google-only allowlist would intentionally break that feature. A school-specific approved-host list or an isolated public-image fetch service is a concrete design choice requiring destination inventory/feature approval first. Secure Web Proxy can enforce hostname/URL egress policies, but provisioning/cost and routing are additional work; [official overview](https://docs.cloud.google.com/secure-web-proxy/docs).

No cloud resources, domains, provider credentials, retention settings, or original workspace files were changed. Network and external-provider behavior remain unverified by these local tests.
