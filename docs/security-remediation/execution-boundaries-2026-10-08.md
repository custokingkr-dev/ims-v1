## SMS report binding

The existing normalized report receiver needs a bridge from an explicitly selected provider contract to its immutable accepted submission. The new bridge verifies internal reporter authority before parsing or database access, reads the accepted inbox and submission under the tenant's row-level security scope, and derives request, correlation and recipient bindings from the locked persisted payload. It reuses the existing append-only report reconciliation and suppression checks in the same bounded transaction. Strict UTF-8 decoding rejects alternate encodings and malformed bytes before JSON parsing.

Independent review found that the preliminary bridge selected `destination`, while the actual SMS transport prefers `mobile`, `phone`, `to` and `recipientMobile`, and also supports `msg91Body` passthrough. An accepted payload can therefore have a valid request hash and still select different recipients in the bridge and sender. The fix narrows the dormant bridge to one canonical digit destination and rejects unsupported routing aliases and passthrough bodies. Existing live sending semantics remain outside this bridge's selected contract.

The bridge has no Spring bean, HTTP endpoint or enabled account configuration. Internal reporter authority does not prove that a report originated from MSG91. Before live admission, select and implement the account's exact API/report versions, vendor authentication, sender/template configuration and approved recipient scope; then prove actual authenticated report binding and recipient outcomes. Preserve UNKNOWN outcomes without automatic resend. MSG91's [webhook documentation](https://msg91.com/help/webhooks/how-can-i-get-the-delivery-reports-on-my-webhook-url) includes several report formats, so one version cannot be inferred for this account.

## Governance command execution

The previous helper used a Windows shell with caller-selected command and branch arguments. The fix resolves a native executable, rejects batch wrappers, passes a fixed GET argument shape without a shell, and validates repository and branch inputs. Streaming limits bound each response and cumulative output; monotonic budgets bound admitted subprocess waits. Error records preserve a useful category without copying raw sensitive output.

Independent review also found that terminating only the direct child could leave a descendant holding a pipe, and that a reader setup failure could escape cleanup. The corrected lifecycle must own the child before execution, terminate its owned process tree, and clean up partially started readers. Controlled tests cover shell metacharacters, output overflow, deadlines, inherited pipes and setup failure. Python documents that Windows [batch files may invoke a shell even with `shell=False`](https://docs.python.org/3/library/subprocess.html#security-considerations), which supports rejecting batch wrappers. Operating-system process creation itself is outside a strict interruptible deadline guarantee.

Passing this verifier does not enforce repository policy. The current account can push but lacks repository administration; the dev branch is still unprotected. A repository administrator must enforce the reviewed required checks and bypass policy and supply independent API readback.

## Isolated source erasure recovery

The new alternate main requires an explicit isolated-dev bootstrap and refuses the ordinary Cloud Run service environment. It creates no Spring application context, web listener, migration runner, scheduler or notification worker. Fixed protected mounts supply a separately provisioned trust policy, signed owner approval, worklist, physical-target wrapper, instance CA and purpose-role credential. Independent owner and freeze signing keys bind the exact clone, numeric private endpoint, database, role, lineage, epoch, object generations and worklist hashes.

The executor checks the actual transaction connection and TLS session, rejects administrative or inheritable database privileges and object ownership, pins tenant scope and search path, and reuses the existing source-erasure owner workflow. It verifies the current signed freeze object before each task and before commit admission. Changed freeze generations or expired leases cause the active task to roll back. Completed tasks retain their durable receipts; failure of a later task does not roll back already committed tasks.

The transport uses the reviewed instance CA and the approved numeric endpoint with `verify-ca`. The CA certificate fingerprint and mounted PEM-file hash are separate bindings. pgJDBC documents that [hostname verification is an additional `verify-full` property](https://jdbc.postgresql.org/documentation/ssl/); this runner does not claim it. Tests use local TLS PostgreSQL and controlled journal objects. They do not establish the identity or lineage of a live Cloud SQL clone.

The signed freeze record is an operator attestation. It does not independently pause every service or provider. Full recovery still requires approved historical and external-only intent coverage, a physical isolated clone, enforced global freeze/drain, downstream and provider reconciliation, recovery-copy purge policy, and governed epoch cutover and resume. This entry point reports source replay only and never authorizes restoration readiness or delivery resume. [Generation preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions) support binding immutable objects, but do not establish complete historical coverage.
