# Additional dev acceptance evidence — 2026-10-07

The bounded live probe used two newly reserved school-bound SCHOOL_ADMIN accounts and synthetic student rows. It issued only 240 student-list GET requests, at two requests per second with at most two in flight. All 240 succeeded; p95 was 422 ms and elapsed time was 127.485 seconds. Budget, logging, freshness, database CPU, memory components and connection guards passed. This small probe is not a peak-load or production-capacity certification. [Measured results](acceptance-bounded-dev-reads.json), [fresh preflight](acceptance-capacity-preflight.json).

The probe started before the final whole-body timeout implementation was loaded. Its requests used bounded per-socket timeouts and completed normally. The stricter final implementation has a real controlled HTTP test for trickled body cancellation, redirect rejection and response size limits; it has not been re-measured under the 240-request live workload. Three controlled Python tests passed. No business rows or credentials are included in these artifacts.

At the same measurement epoch, Cloud SQL memory components were Usage 14.625093%, Cache 14.696682%, Free 70.678225% (sum 100%). The raw `memory/usage` gauge equalled the quota, while `memory/total_usage` was about 154 MB. These gauges describe different scopes and must remain visible rather than being presented as interchangeable memory utilization. Google's [PostgreSQL memory guidance](https://docs.cloud.google.com/sql/docs/postgres/optimize-high-memory-usage) specifically recommends alerting on the Usage component approaching 90% and describes available cache/free memory. The bounded probe therefore used that documented component guard, preserving CPU and connection guards. [Component descriptors and measurements](acceptance-memory-components.json).

Synthetic privacy checks passed in isolated PostgreSQL test containers: five export/checksummed tenant-erase checks, one actual student repository transaction test, and twelve platform projection tests. The repository test proves rollback preserves the target and suppresses photo cleanup; commit deletes the target, emits a deletion event, and invokes the controlled photo provider after commit while retaining the control tenant. The restore test reconstructs a stale synthetic snapshot with delivery stopped, replays the separately retained erasure intent twice, suppresses a late upsert/delivery, and makes zero provider calls. [Sanitized evidence](acceptance-privacy-synthetic.json).

The restore test retains deletion intent outside its synthetic backup in the test fixture. An operational durable external erasure journal is still required before this can be certified as a real recovery process. These tests do not prove cloud object removal, real external-provider deletion, approved retention policy, or production offboarding. No actual business data was erased. Proposed dev-only recovery targets of 15-minute RPO and 30-minute RTO remain proposals awaiting owner approval; existing seven-day backup retention was not changed.

Old revision traffic absence is not physical drain proof. Cloud Run can retain idle instances, as described in its [autoscaling documentation](https://docs.cloud.google.com/run/docs/about-instance-autoscaling). The separate read-only inventory preserves current and secure rollback revisions and merely identifies obsolete unsafe revision candidates. Cloud Run [revision deletion cannot be undone](https://docs.cloud.google.com/run/docs/managing/revisions); no revision deletion is authorized by this evidence file or was performed by its collector.
