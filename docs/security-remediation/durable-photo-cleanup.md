# Durable student photo cleanup

The old deletion path registered an in-memory after-commit callback and logged/swallowed object failures. A process crash or failed object deletion could therefore leave a photo with no durable retry intent. Student deletion now inserts `tenant_school.photo_cleanup_outbox` rows in its existing database transaction, correlated with the precommit erasure operation ID. Rollback leaves neither source erasure nor cleanup intent committed. No object API is called inside the deletion transaction.

The existing machine-authenticated Scheduler outbox endpoint drains up to five cleanup intents. It claims work with `FOR UPDATE SKIP LOCKED`, a fresh UUID lease token and a 60-second lease in a short transaction. Metadata reads and object deletes run outside database transactions. The exact configured bucket and school UID/student prefix are required; external URLs, another bucket, another school/student key and path traversal are never cleanup candidates. Source identity recreation blocks the intent for operator review.

The first worker attempt reads only the exact object's generation, then commits that generation before deleting it with a generation-match precondition. Retries retain the pinned generation and never resolve a newer generation. Missing original generations or conditional replacement conflicts are idempotent success; replacement objects are not deleted. Stale lease tokens and expired leases cannot pin or complete work. Retry errors are fixed reason codes, without raw provider errors, object keys or credentials. Backoff is bounded at one hour; intents survive retries without an automatic discard limit or purge. Completed/blocked evidence retention is left to an approved policy.

The dedicated object client uses one SDK attempt, two-second connect and five-second RPC/read settings. A two-slot daemon executor adds a six-second complete-call limit around credential acquisition and object operations. Timeout cancels the attempt; SDK operations that ignore interruption can consume at most those two slots, causing further attempts to fail closed rather than grow an unbounded queue. The batch begins no new work after 25 seconds; an already admitted bounded operation may finish afterward. No object request holds a database transaction.

Forward migration `tenant_school/V30__durable_photo_cleanup.sql` adds the machine queue and grants baseline/dedicated runtime SELECT/INSERT/UPDATE capabilities through the existing ACL callback, without DELETE or public grants. This operational outbox follows the existing cross-tenant event-outbox pattern; it has no public tenant query surface and no parent FK that could remove erased-identity evidence. The public student deletion response and domain event remain unchanged. The internal relay response adds `photoCleanupCompleted`.

Final owned validation passed **23 tests, zero failures/errors/skips** across the real PostgreSQL/object-client durability class (8), storage (8), existing delete/event repository (5), Scheduler controller (1), and opt-in actual student-delete rollback/durable-intent test (1). The eight durability cases include native concurrent row locking, dedicated-runtime migration ACLs and whole-call timeout. In the combined run, 21 separate absentee tests also passed, while a new owner-policy fixture initially failed a legitimate policy constraint. A subsequent separate real PostgreSQL run passed the corrected three owner-policy cases; no constraint was weakened. Photo log: `tmp/photo-cleanup-final-tests.log`. This is implementation evidence using controlled object clients, not proof that a live cloud object was deleted. No live cloud object or source business row was touched. Historical completed callbacks without a recorded object key cannot be reconstructed automatically; no bucket-wide listing or deletion is introduced.

Google documents generation-qualified deletion as safe to retry without deleting replacements: [request preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions), [retry strategy](https://docs.cloud.google.com/storage/docs/retry-strategy). This worker does not prove physical expungement of soft-deleted data or prior noncurrent versions. It neither enumerates historical versions nor changes bucket retention/soft-delete policy; those remain owner-approved policy work.


## Default-ACL correction

The local `deploy/local/initdb/00-app-rt.sql` and operator `scripts/create-app-rt-role.sql` grant owner-created tables baseline DML through default ACLs. Granting SELECT/INSERT/UPDATE alone does not remove an already inherited direct DELETE grant. V30 now explicitly **REVOKE ALL FROM app_rt before granting only SELECT/INSERT/UPDATE**, and separately revokes PUBLIC. The existing dedicated-role callback therefore copies the reduced baseline rather than a residual DELETE permission.

It executes both actual repository bootstrap scripts before creating the queue, proves their default DELETE grant is active on a probe table, additionally models broad legacy ALL defaults, then applies V30. A separate database runs the complete tenant_school and student Flyway chains and repeats the actual per-schema callbacks twice. Both baseline and dedicated roles individually allow SELECT/INSERT/UPDATE and deny DELETE/TRUNCATE/REFERENCES/TRIGGER. Enqueue, claim, generation pin and completion execute successfully under `SET LOCAL ROLE ims_school_core_rt`; actual DELETE/TRUNCATE attempts fail and preserve the completed evidence.

This scopes the guarantee to owner bootstrap **before** forward migrations and repeated migration callbacks afterward. Reapplying an administrator's blanket runtime grants after these migrations is an independent privileged ACL change and is not made safe by this migration alone.
