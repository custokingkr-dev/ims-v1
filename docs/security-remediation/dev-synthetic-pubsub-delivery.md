# Dev synthetic reporting delivery and resilience drill

On 2026-10-07, the existing dev reporting topic and authenticated Pub/Sub push delivered a marked reporting-only student envelope. Publishing that exact event twice produced one processed inbox row and one student projection. No school-core student row, billing transaction, workflow or notification delivery was created. The two reserved schools were independently provisioned for acceptance; a read-only owner query first verified their fixture marker and proved the separate reporting-only student IDs were vacant in owner students, projections and tombstones.

A nonce-owned isolated push subscription used the same platform endpoint and existing reporting push identity. Its synthetic envelope with an invalid schema marker was forwarded by the real broker to an isolated dead-letter topic. Only that private synthetic inspection subscription was pulled. The verified envelope was repaired by restoring its schema marker, published to the actual reporting source, and acknowledged only after publish succeeded. Readback then confirmed two processed inbox events and two reporting projections. This demonstrates real broker dead-letter forwarding and repair/replay, using five approximate delivery attempts and 1..5-second retry delays for the bounded drill; the deployed source remains at ten approximate attempts and 10..600-second retries.

Cleanup published deletion envelopes for those two reporting-only IDs. Marker-only SQL counts confirmed four processed inbox records, zero student projections and two durable tombstones. The temporary topics, subscriptions and their resource-scoped IAM grants were deleted; a project metadata readback found zero drill topics or subscriptions. No shared inspection queue was pulled, peeked, acknowledged or replayed. No emails, SMS, WhatsApp messages or real business events were sent.

The saved JSON contains counts, stages, timestamps and operational identifiers only. The helper uses fixed dev project/fixture IDs, strict synthetic event and field validation, isolated queues, exact nonce cleanup, bounded native/API calls, and no secret-value reads; the owner database password remains a Cloud Run job secret reference. Seven controlled offline tests cover scope, shared-queue rejection, marker binding, contact-field rejection, redirects, cleanup and safe native failures.

Consumer restart, in-flight crash recovery, real backlog drain and notification provider receipt are separate acceptance checks and are not claimed by this drill. Two preliminary attempts stopped before publishing or creating broker resources: a too-narrow status-URL alias check and structured-log JSON extraction. Both were corrected before the successful run, and their temporary verification jobs were removed.

Google documents dead-letter forwarding as best effort and approximate in [Dead-letter topics](https://docs.cloud.google.com/pubsub/docs/dead-letter-topics). The concrete evidence is in `dev-synthetic-pubsub-delivery-proof.json`; the reproducible operator helper is `scripts/security/dev-synthetic-pubsub-drill.py`.
