# Provider wire contract hardening, 2026-10-08

The MSG91 submission and report boundaries must interpret one complete JSON document. The previous generic SMS and EMAIL acknowledgement parsers used the application's permissive mapper: duplicate fields could overwrite an uncertain outcome with success, and trailing documents could be ignored. An offline regression run reproduced four failures, including an ambiguous prepared SMS routing body reaching the synthetic transport. The response subscriber also replaced malformed UTF-8 bytes instead of rejecting the response.

The fix uses an independent strict parser for provider wire contracts, including prepared routing bodies and delivery reports. Duplicate names, including escaped equivalents and nested duplicates, and trailing JSON tokens are rejected. The bounded response subscriber reports malformed UTF-8 rather than replacing it; valid Unicode split across response chunks remains supported. These are interpretation controls, not evidence that MSG91 accepted or delivered a message. [RFC 8259 sections 2, 4 and 8](https://www.rfc-editor.org/rfc/rfc8259.html) explain the single-value grammar, differing duplicate-name interpretations and UTF-8 interoperability requirement.

EMAIL HTTP outcomes are also more conservative. The [MSG91 Email Error Codes guide](https://msg91.com/help/email/email-rejection-types-and-error-codes) documents direct refusal meanings for HTTP 401/403/404/422. Those statuses require a strict single JSON object without contradictory known EMAIL acknowledgement fields. A positive queue body, duplicate fields, trailing tokens, malformed JSON or incompatible acknowledgement types remain `UNKNOWN`. HTTP 400/405/413/415 no longer become definitive rejection from their status alone; 402 remains `UNKNOWN` because its account-selected endpoint contract has not been established. No vendor-specific refusal JSON schema or automatic resend is introduced.

The existing EMAIL callback rejects ambiguous bytes before its durable report transaction; actual MockMvc regressions verify that duplicate status, escaped duplicate provider ID and trailing documents make no ledger calls or commits. The generic provider builder also rejects ambiguous payloads for all four channels, with ordinary valid SMS/OTP/EMAIL/WhatsApp controls preserved. Authentication order, routes, field schemas, body caps and live-admission guards are unchanged.

Source/local verification is indexed in [the exact local record](acceptance-parallel-hardening-provider-local.json). The four initial red regressions, passing focused checkpoints and an earlier full-run HTTP fixture failure are retained separately. That earlier oversized incomplete chunk was rejected with 408 rather than its required 413; its focused repeat passed without changing the body reader or relaxing its expected status. A passing repeat does not establish the earlier failure's cause. The final source's full test result and later CI/dev rollout have separate evidence and must not be added to overlapping focused counts.

| Controlled provider exercise | Supply verified sender/domain/template configuration, managed secret references and approved recipient scope, then test acceptance, authenticated bound delivery reports, restart/idle durability and UNKNOWN-no-resend.
