# Owner replay preparation, 2026-10-08

The new `scripts/security/prepare-dev-owner-erasure-replay.py` converts the validated historical coverage bundle into full generation-pinned work items suitable for the existing owner `StudentReadRepository.reconcileErasure(IntentReference)` method. Unlike the older synthetic 20-target SQL prototype, it retains immutable incarnation, original epoch, operation, canonical intent and exact external object/generation/SHA. It emits no destructive SQL, connects to no database or cloud service, and does not execute owner replay.

`plan`, `snapshot-sql` and `reconcile` require the reviewed canonical bundle hash and existing bounded regular-file parsing. Output creation is exclusive. The snapshot SQL is repeatable-read/read-only, has statement/lock deadlines and sets `row_security=off`: callers whose RLS would hide rows fail instead of certifying absence. It compares exact source identity and all receipt fields, including generation as bigint. Reused IDs, wrong school/incarnation, mismatching receipts and conflicting operation/incarnation-epoch receipts are quarantined. An external-only absent source is explicitly unproven; a matching SQL receipt proves only source erasure receipt matching, not downstream or physical object erasure. Every supplied intent must have exactly one known observation; partial, duplicate, unknown and foreign results fail. Observation JSON is untrusted snapshot input, not independently attested execution evidence.

The initial ten-test checkpoint is retained. After independent review, fourteen final local tests passed with no skips or failures; seven use an isolated PostgreSQL 16 container. They cover precision above 2^53, historical epochs, exact-source versus reused-ID conflict, receipt generation/operation mismatch, cross-school/incarnation rejection, read-only write refusal, RLS-hidden-row refusal and complete outcome accounting. The first development run exposed a multiline PostgreSQL JSON formatting mismatch; jsonb aggregation corrected that parser boundary before the final passing run. Container removal ran in test teardown. No business rows, cloud objects, clones or provider traffic were accessed.

Existing Java `StudentErasureJournalIntegrationTest` already covers generation-pinned reconciliation through the full owner transaction, idempotence for a proven absent target and refusal to erase reused IDs or claim unproven absence. Those tests were inspected, not rerun or counted as this tool's fourteen tests.

## Remaining execution prerequisites

A full runner still needs a separately authenticated owner-only isolated bootstrap that starts neither web listeners nor schedulers/outbox/photo workers, approved clone and database/lineage binding, and an independently verifiable all-service write/delivery freeze capability held throughout replay. The ordinary Spring application is unsuitable as that bootstrap. The current catalog verifier is read-only physical attestation, not such an execution capability. No runtime/public route, owner credential transport, bypass of live generation reads, epoch change or resume switch is added.

Independent exhaustive old-epoch inventory and physical generation reads, approved pre-journal/legacy lineage mapping, externally authorized clone/cutover, complete downstream tombstone/inbox/fact/provider reconciliation, physical photo recovery-copy handling and owner-approved retention/RPO/RTO remain required. All outputs retain `restorationReady=false` and `deliveryResume=false`. Local reconciliation advances replay preparation; it does not close full governed recovery.
