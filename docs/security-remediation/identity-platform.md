## Configuration contract

All five Java services:

- `RUNTIME_DB_ROLE`: `ims_identity_rt`, `ims_school_core_rt`, `ims_operations_rt`, `ims_platform_rt`, `ims_billing_rt` respectively after owner-run cutover. `app.runtime-db-schemas` is fixed in each service YAML; known schemas are validated.
- `SERVICE_OIDC_AUDIENCES`: exact receiving service URL aliases, not arbitrary caller audiences.
- `USER_CONTEXT_CALLER_SERVICE_ACCOUNTS`: exact gateway service account; school additionally identity account only for validated delegation.
- `X-IMS-Principal-Carrier-Token: Bearer <signed Google metadata ID token>`: independent signed principal-carrier token. Cloud Run's signature-stripped `X-Serverless-Authorization` is never decoded as authority. Gateway strips client copies.
- Per machine route: `OUTBOX_RELAY_CALLER_SERVICE_ACCOUNTS` (`/api/v1/internal/outbox/relay`), `BROADCAST_POLICY_CALLER_SERVICE_ACCOUNTS` (`/api/v1/internal/notifications/broadcast-recipients` and `/fee-reminders` child), `IDENTITY_DIRECTORY_CALLER_SERVICE_ACCOUNTS` (`/api/v1/internal/identity-directory/{schools|zones}/{id}`), `PASSWORD_RESET_DRAIN_CALLER_SERVICE_ACCOUNTS` (`/api/v1/internal/password-reset/drain`), `ASYNC_DRAIN_CALLER_SERVICE_ACCOUNTS` (`/api/v1/internal/async/drain`), `NOTIFICATION_DELIVERY_CALLER_SERVICE_ACCOUNTS` (`/api/v1/internal/notifications/deliveries`). Missing allowlist fails closed.
- Signed application OIDC is in `Authorization`; send the same token in `X-Serverless-Authorization` for IAM when required so the independent signed Authorization survives. Never accept a signature-removed token.

Identity:

- `APP_JWT_ISSUER=ims-identity`, `APP_JWT_AUDIENCE=ims-api`, `APP_JWT_PREVIOUS_SECRET` only during rotation; refresh audience is `ims-identity-refresh`. Gateway has no default minting secret.
- `IDENTITY_WEBAUTHN_RP_ID`: exact canonical frontend hostname; `IDENTITY_WEBAUTHN_ORIGINS`: explicit HTTPS origin(s) belonging to that RP. Do not use the shared `run.app` parent as RP. Status returns configured `rpId`/`canonicalOrigin` so clients can explain alias mismatch.
- `IDENTITY_COOKIE_ALLOWED_ORIGINS`: exact reviewed frontend aliases, independent of canonical WebAuthn origin.
- `IDENTITY_PASSWORD_RESET_WORKER_READY=true` only after a real authenticated scheduler or always-allocated worker is verified. Scheduler POSTs reset drain with exact identity-service audience and allowlisted account. One message/trigger requires a cadence matching expected reset volume. ## Passkey recovery runbook

1. Prefer the account's second enrolled authenticator. It performs a fresh assertion, not password-only downgrade.
2. A different SUPERADMIN with a fresh passkey assertion submits `POST /api/v1/auth/passkeys/recovery/request` with target `userId` and bounded verified-identity `reason`.
3. Within ten minutes, a second different SUPERADMIN with a fresh assertion submits `/recovery/approve` using `recoveryId`. Target, requester and approver must be distinct. Requester cannot approve their own request; expired/completed requests fail.
4. The transaction increments target credential version, revokes all target sessions, deletes all target challenges/step-up/factors, and records trusted request/completion audit. Target must password-login, enroll again, then assert before privileged work. Approval never grants target step-up.
5. If all independent privileged authenticators are lost, the online API stays closed. Use a separately reviewed, identity-verified owner maintenance procedure with two-person authorization and preserved audit; there is no password-only emergency API.

## Database rollout

Run `runtime-role-cutover.sql` as owner to prepare safe dedicated roles/owned schema grants; set passwords through managed secret tooling without logging them. The script preserves app_rt until coordinated cutover. Each schema's `afterMigrate__dedicated_runtime_acl.sql` copies only existing app_rt owner-schema table/column, sequence and callable-function privileges; it does not grant owner-only reconciliation functions or foreign schemas. Future owner migrations synchronize these ACLs before traffic. FORCE RLS owner backfills explicitly set transaction-local bypass. Runtime credentials never run owner migrations; the separate migration-only process is isolated from runtime Spring startup.

Rollback must preserve new tenant guard/role constraints and tombstones. Do not restore broad shared runtime credentials or remove MFA requirements to make a rollout pass. A pre-binding token revision cannot validate newly bound tokens; rollback compatibility requires deliberate key/token migration planning.

### Cloud Run runtime admission before Flyway

Every service's identical `MigrationRuntimePolicy` now rejects nonblank `K_SERVICE` unless `APP_MIGRATIONS_ENABLED=false` is explicitly configured and `RUNTIME_DB_ROLE` equals the dedicated role for the single application class packaged in that image. The role binding is imposed on `app.runtime-db-role` before bean creation, so a lower-level override cannot select the shared role. Missing, shared, owner, other-service and ambiguous/unknown image role configurations fail before Flyway; owner credentials remain forbidden on migration-disabled servers. The standalone owner-only `MigrationOnlyMain` does not create Spring and remains usable by migration jobs. Local execution without `K_SERVICE` retains the existing migration default.
