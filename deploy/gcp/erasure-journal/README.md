# Dev erasure journal

This dedicated module manages five resources in `custoking-dev`: a private versioned GCS bucket, two custom roles, and two conditional runtime bindings. Its separate backend is `gs://custoking-dev-terraform-state/security/erasure-journal/dev/default.tfstate`. It does not change Cloud Run traffic, production, or the existing observability state.

The school runtime can create/read `intents/` and read `control/`. It cannot list, replace, update, delete, or activate a control object. All resources have `prevent_destroy`; bucket public access is prevented. No expiry or irreversible retention lock is inferred from an unapproved retention policy. Versioning and IAM restrictions do not prevent a privileged owner from deleting objects.

Run `python scripts/security/provision-dev-erasure-journal.py` from the repository for a read-only exact-scope plan. Only the explicit `--apply-dev` flag applies a reviewed saved plan. Updates, deletions, replacements, unrelated resources and broader privileges are rejected. The default report goes to `tmp/`, preserving curated acceptance evidence. Temporary credentials remain in a verified workspace temporary directory and are removed after execution.

`dev-source-control.json` records the initial source epoch. Its exact LF-terminated bytes and existing object generation are pinned by the dev deployment parameters. The configuration renderer rejects a foreign project/database/bucket or an unreviewed control tuple. Production remains disabled. The actual dev infrastructure, control readback and runtime permission checks are recorded in [the infrastructure proof](../../../docs/security-remediation/acceptance-dev-erasure-journal-infrastructure.json), [control proof](../../../docs/security-remediation/acceptance-dev-erasure-journal-control.json) and [runtime proof](../../../docs/security-remediation/acceptance-dev-erasure-journal-runtime-permissions.json).

The source contract creates and reads back the immutable external intent before committing a confirmed student erasure. A SQL rollback cannot undo that intent. Current-owner delivery checks deny when the intent exists or its lookup/control verification fails. Photo cleanup commits a generation-pinned retry queue alongside source deletion. See [the source contract](../../../docs/security-remediation/precommit-erasure-contract.md) and [photo cleanup](../../../docs/security-remediation/durable-photo-cleanup.md).

A restored database must stay frozen and drained. An operator must verify its physical clone/source binding, establish complete external intent coverage (including old epochs and pre-incarnation legacy records), set the reviewed control to `RECONCILING`, run exact-generation replay with all dependent stores fenced, and independently verify convergence before an explicitly reviewed new activation. The application replay method is not a public endpoint and never resumes delivery or activates an epoch. This initial control object and local replay fixtures do not certify that full recovery procedure, physical object/provider purge, or an approved RPO/RTO.
